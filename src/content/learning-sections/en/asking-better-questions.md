# Asking Better Questions

Asking for help is part of learning Computer Science. The quality of the question affects how quickly someone can help and how much you learn from the answer. A vague question such as "my code does not work" forces the helper to discover the assignment, the expected result, the actual result, and what you already tried. A better question gives that context upfront and points to the exact place where you are stuck.

A strong help request has four parts: context, attempt, observation, and question. Context names the assignment or concept. Attempt shows your current reasoning or code summary. Observation explains what happened. The question asks for the next step, not for someone to complete the whole task. This structure respects your own learning because it keeps you involved in the problem.

| Question part | Weak version | Stronger version |
| --- | --- | --- |
| Context | "This exercise" | "The exercise asks for the average of three grades" |
| Attempt | "I tried everything" | "I added the grades and stored the sum" |
| Observation | "It is wrong" | "It prints 21 instead of 7" |
| Question | "Can you fix it?" | "Where should the division happen?" |

Before asking, create a minimal example when possible. Remove unrelated code and keep only the part needed to show the issue. This is not busywork. Many students find the answer while reducing the problem because the unnecessary details stop hiding the cause. The [Stack Overflow guide on minimal reproducible examples](https://stackoverflow.com/help/minimal-reproducible-example) is written for public programming questions, but the same habit helps in class, group chats, and office hours.

Be honest about what you tried. Do not write "nothing works" if you tested one input. Instead, name the input and result. Do not hide confusion behind technical words you do not understand. A question like "I think the loop condition is wrong because it stops before the last value" is useful even if your diagnosis is imperfect. It gives the helper a place to start.

Ask for explanation, not only correction. If someone sends fixed code and you paste it without understanding, the next similar exercise will feel new again. Try asking, "Why does this condition use `<` instead of `<=`?" or "How did you know the sum was correct but the average was not?" These questions turn the answer into a reusable idea.

Tone matters too. Helpers are more willing and able to respond when the question is respectful, specific, and complete. Include code or screenshots only when they add evidence. If an error message appears, copy the important line exactly and say when it appears. If the platform has rules about formatting questions, follow them. The [Computer Science Stack Exchange help center](https://cs.stackexchange.com/help/how-to-ask) gives useful general guidance about focused technical questions.

Good questions also help you decide where the problem belongs. Is it vocabulary? Then ask for a definition. Is it logic? Show the steps you expected. Is it syntax? Include the error message and relevant line. Is it debugging? Provide the reproduction case. Naming the problem type helps you choose the right helper and resource.

In group work, better questions prevent accidental dependency. Instead of asking a teammate to "do the accessibility part", ask "Can you review whether the tab order matches the visual order on this page?" The second question is specific, testable, and connected to a shared goal.

## Practice routine

Rewrite this vague question: "My loop does not work." Add the assignment goal, the input you used, the output you expected, the output you saw, and the exact point where you are unsure. Keep it short enough that someone can answer in a few minutes.

## What to do next

Before your next help request, fill in four sentences: "I am working on...", "I tried...", "I expected...", and "I am stuck at...". If one sentence is missing, gather that evidence first.
